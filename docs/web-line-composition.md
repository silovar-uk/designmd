# Webの行と文章の設計

対象：AIが生成・編集するWebページ、LP、コラム、特設サイト、Web資料、HTMLスライド。

> 紙を模倣せず、紙の編集密度を、変化する画面の上で再構成する。

Webの一行は固定された版面の部品ではない。文章、画面幅、文字倍率、書体、ブラウザ、読者の設定が出会った瞬間にだけ成立する一時的な形である。したがって、制作者が固定するのは行末ではなく、意味のまとまり、優先順位、読ませ方、破綻しない条件である。

## 1. 基本思想

### 意味は固定し、行は流動させる

AIは意味構造を決めてよいが、すべての端末で同じ行末を命令しない。`<br>`は文章上の改段ではなく視覚上の固定命令であり、画面幅が変わると二重改行や孤立語を生みやすい。

### 紙の外見ではなく、編集倫理を持ち込む

紙雑誌から受け継ぐのは、明朝体、段組み、紙テクスチャではない。

- 読者の注意を雑に扱わない
- 意味単位を壊さない
- 一行ごとの視線移動を考える
- 重要度を形として示す
- 読ませる速度を意図的に変える

### 組版は透明だが、中立ではない

文字組みは内容を邪魔しない器である一方、何を先に見せ、どこで止め、どこを同じまとまりとして扱うかを決める。目立たなくてよいが、無自覚であってはいけない。

### Web固有の変化を受け入れる

Webは画面幅、文字拡大、入力方法、読み上げ、縦横切替によって姿を変える。完成時のスクリーンショット一枚ではなく、変化しても編集意図が薄まらないことを品質とする。

## 2. 文章の役割ごとに折り返し方を変える

| 要素 | 目安 | 折り返し方針 |
|---|---:|---|
| 大見出し | 1〜3行、約12〜22字／行 | 意味単位を優先し、`balance`を漸進適用 |
| 小見出し | 1〜3行、約14〜26字／行 | 内容を特定できる文言にし、孤立語を避ける |
| リード | 全角24〜32字程度／行 | 本文より狭くし、結論と読み進める理由を置く |
| 本文 | 全角28〜36字程度／行 | `strict`な禁則、十分な行間、自然な右端 |
| 引用 | 全角20〜30字程度／行 | 本文より狭くし、発言の呼吸を残す |
| キャプション | 全角20〜32字程度／行 | 画像との関係を一文で説明する |
| ボタン・タグ | 原則1行 | 短く書き直し、意味的に分割しない |
| URL・コード | 内容次第 | 通常は単語を守り、はみ出す長トークンだけ救済 |

数字は絶対値ではない。書体、文字サイズ、読者、媒体、段組みで調整する。40字は目標ではなく、本文が長くなりすぎないための上限として扱う。

## 3. 見出しを文章ではなく構図として編集する

見出しの折り返しは、ブラウザへ全文を投げて終わりにしない。次の順で判断する。

1. 意味のまとまり
2. 読者が最初に拾う語
3. 上下の行の視覚的な長さ
4. 最終行の短さ
5. 行数
6. 文字サイズ

### 避ける状態

- 助詞だけが次の行へ残る
- 2〜4文字だけの最終行が生まれる
- 固有名詞が不自然に分割される
- 数字と単位が離れる
- 1行目が極端に長く、2行目が極端に短い
- スマホだけ文字を縮小して1行へ押し込む
- PC用の固定`<br>`がスマホで二重改行になる

### 固定改行を使える条件

次をすべて満たす場合に限る。

- 見出し自体が短い
- 分割位置に意味上の理由がある
- 320pxから1440pxまで主要幅で確認した
- 200％文字拡大でも意味と操作を損なわない
- CMSや翻訳で文言が変わらない
- 固定改行を外した時より明確に良い

一つでも満たさなければ、固定改行ではなく最大幅、文字サイズ、意味単位、`text-wrap`で調整する。

## 4. 折り返さない単位を限定する

`white-space: nowrap`はレイアウトを支配する命令ではなく、短く分割不能な単位を守るために使う。

適用候補：

- 人名、短い固有名詞
- 日付、時刻
- 数字＋単位
- 章番号
- 短いタグ
- ボタンラベル
- スコア、比分

長い見出し、文章、説明文全体へは使わない。収まらない時は文字を極端に縮めず、文言、配置、幅を見直す。

```html
<p>
  来場者数は<span class="no-break">52,000人</span>でした。
</p>
```

## 5. 日本語組版の最低品質

- 行頭へ句読点、閉じ括弧、長音記号などを不自然に出さない
- 行末へ開き括弧を残さない
- 連続するダッシュ、省略記号を途中で割らない
- 欧文単語を理由なく文字単位で分割しない
- `word-break: break-all`を本文全体へ使わない
- 長いURLや識別子だけ、局所的に`overflow-wrap: anywhere`で救済する

厳しい禁則ですべてを守ることが常に最善とは限らない。狭い見出しでは字間の乱れと禁則のどちらを優先するかを決め、一貫させる。

## 6. CSSの標準実装

```css
:root {
  --measure-body: 36em;
  --measure-lead: 30em;
  --measure-heading: 18em;
}

.article-title,
.section-title {
  max-inline-size: var(--measure-heading);
  line-break: strict;
  word-break: normal;
  overflow-wrap: normal;
  text-wrap: balance;
}

.article-lead {
  max-inline-size: var(--measure-lead);
  line-height: 1.75;
  line-break: strict;
  text-wrap: pretty;
}

.article-body,
.article-body p,
.article-body li {
  max-inline-size: var(--measure-body);
  line-height: 1.8;
  line-break: strict;
  word-break: normal;
  overflow-wrap: break-word;
  text-wrap: pretty;
}

.no-break {
  white-space: nowrap;
}

.long-token {
  overflow-wrap: anywhere;
}

@supports (word-break: auto-phrase) {
  .article-title,
  .section-title {
    word-break: auto-phrase;
  }
}
```

`text-wrap: balance`と`pretty`、`word-break: auto-phrase`は対応状況が変わるため、未対応でも読める通常の折り返しを基礎にする。機能の有無で意味が変わってはいけない。

## 7. AIへ渡す構造

AIへHTMLを直接一発生成させる前に、見出しごとに次を出させる。

```text
見出し本文：
役割：内容説明／解釈／判断／転換
最大行数：
優先して同じ行へ置く句：
分割禁止：
折り返し候補：
固定改行が必要か：原則不要
スマホで短縮可能な表現：
```

AIの役割は意味の楽譜を作ること。最終行末はデザインシステムとブラウザが、その閲覧環境で演奏する。

### AIの禁止事項

- 意味上の理由なしに`<br>`を入れる
- すべての見出しへ固定改行を入れる
- `word-break: break-all`で問題を隠す
- 収まらない文字を極端に縮小する
- PCのスクリーンショットだけで完成判定する
- 全文を同じ`max-width`、同じ行間で扱う
- ボタンを2行にして文言の長さを放置する
- 日本語見出しと同じ意味の英語ラベルを重ねる

## 8. Web文章の読み方を設計する

Webでは精読だけでなく、探索、比較、判断、行動のためにも文章が読まれる。すべてを短く切るのではなく、読者が読み方を切り替えられる構造を作る。

- 見出しだけを読んでもページの論理が追える
- 各段落の冒頭に対象または判断を置く
- 重要情報を右側や段落末尾だけへ隠さない
- 精読させたい本文は十分な行幅と余白を持つ
- 行動文は、対象、条件、操作、結果を明確にする
- カード化は独立した入口に限り、連続文章を細切れにしない

## 10. 品質検査

### 幅を連続的に動かす

代表幅のスクリーンショットだけでなく、320pxから1440pxまでブラウザ幅をゆっくり動かす。変な状態はブレークポイントの間に出やすい。

### 必須確認

- 320、375、768、1024、1440px
- 200％文字拡大
- OSの文字サイズ変更
- 日本語と英数字が混ざる見出し
- 長い固有名詞、URL、数値＋単位
- CMSで最長文言を入れた状態
- 日本語IME、読み上げ、キーボード操作

### 見出しレビュー

- 見出しだけでページの論理が追えるか
- 最終行が極端に短くないか
- 助詞や接続語が孤立していないか
- 固有名詞、数字、単位を壊していないか
- 手動`<br>`を外した方が安定しないか
- 幅変更時に文字サイズが過剰に変化しないか

### 本文レビュー

- 行末から次の行頭へ視線を戻しやすいか
- 行幅に対して行間が狭すぎないか
- 段落が長すぎて探索点を失っていないか
- 右端の凹凸が極端な短長の反復になっていないか
- URL対策のために通常の日本語まで文字単位で割っていないか
