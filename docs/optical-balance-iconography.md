# 光学バランスとUIアイコン

> 状態：experimental  
> designmd版：2026.08.13-beta  
> 最終更新：2026-08-13  
> 起点：Quick LinksのFABにおける「＋」の視覚的な中心ずれ

UIの部品は、CSS上で中央に置かれていても、見た目では中央に見えないことがある。

フォントの字形、baseline、line-height、線の量、形の方向性、周囲の余白が、知覚上の重心を変えるためである。

> 配置を数値だけで揃えず、知覚上の重心まで揃える。ただし、目分量の補正値を各所へ散らさず、描画規則として一元化する。

この文書は、Web・アプリの操作アイコン、丸ボタン、ナビゲーション、開閉記号などを整えるときの判断基準を定める。

---

## 1. 先に分ける：文字か、機能アイコンか

`＋`、`×`、`−`、`…`、矢印、絵文字は、見た目が文字に近くても、操作部品の中では機能アイコンとして働くことがある。

### 文字として扱う

- 本文中の記号
- 数式や引用の一部
- 入力値そのもの
- 表現として絵文字を使うコンテンツ

### 機能アイコンとして扱う

- 追加
- 閉じる
- 削除
- 検索
- ナビゲーション
- その他メニュー
- 開閉状態

機能アイコンをフォントの字形へ依存させると、OS、フォント、fallback、拡大率によって字面と重心が変わる。

主要操作では、文字を「アイコンの代用品」として使わない。

---

## 2. 描画方法は役割で選ぶ

### A｜SVG：意味を持つ機能アイコンの基本

検索、リンク、設定、編集、閉じるなど、形そのものが操作の意味を伝える場合に使う。

利点：

- 共通の座標系を持てる
- 線幅、端点、角、余白を制御できる
- `currentColor` で状態色を共有できる
- フォントやOSの字形差から独立できる
- 同じアイコンを複数箇所で再利用できる

### B｜CSS geometry：単純な状態記号

`＋ / −` の開閉など、二本の線だけで成立し、状態変化が単純な場合に使える。

利点：

- DOMを増やさず状態変化を表現できる
- 横線、縦線を同じ中心へ置ける
- フォント字形を使わずに済む

ただし、複雑な意味をCSS図形だけで再現しない。

### C｜文字・絵文字：内容として使う

表現や文章の一部として必要な場合に限る。主要な操作経路では、端末ごとに見た目が変わる絵文字へ意味を依存させない。

---

## 3. 五つの原則

### 1. 共通の座標系を持つ

同じアイコン群では、原則として共通の `viewBox` を使う。

Web UIでは `0 0 24 24` を基準にすると、既存資産との互換性を取りやすい。

重要なのは24という数字そのものではなく、**同じ階層のアイコンが同じ座標空間で比較できること**。

### 2. 線の文法を揃える

同じ階層では、次を揃える。

- stroke width
- line cap
- line join
- 塗り／線の使い分け
- 角の丸み
- 内側の余白

一つだけ線が太い、角が鋭い、面積が大きい状態を放置しない。

ただし、単純な `＋` は複雑な歯車より線が少ないため、同じstrokeでも弱く見えることがある。**同じ数値ではなく、同じ視覚強度を目標にする**。

### 3. アイコンサイズとヒット領域を分ける

アイコンを押しやすくするために、絵そのものを大きくし続けない。

目安：

- 補助操作：18px前後
- ナビゲーション：20px前後
- 強い単独操作：24〜26px前後
- タップ領域：40〜48px以上を基本

案件、OS、アクセシビリティ要件に合わせて調整する。

### 4. 幾何学中央のあとに光学中央を見る

最初は中央へ正しく配置する。

```text
icon center = container center
```

その後に確認する。

- 左右の黒量が偏って見えないか
- 上下の黒量が偏って見えないか
- 斜線が片側へ引っ張って見えないか
- 円や三角のovershootが必要か
- 隣の文字やアイコンと並べたときだけ小さく見えないか

補正が必要なら、個別のボタン位置ではなく、アイコン定義側へ閉じ込める。

### 5. 例外値を増やさない

次のような修正が増え始めたら、局所調整を止める。

```css
transform: translateY(-1px);
margin-left: 1px;
line-height: 0.92;
```

一件だけなら直っても、アイコンが増えるほど規則が崩れる。

先に確認する。

1. 文字記号を機能アイコンに使っていないか
2. 座標系が揃っているか
3. SVG自体の余白が不均一でないか
4. line cap / stroke widthが揃っているか
5. container側とicon側の責任が混ざっていないか

---

## 4. コンテナとアイコンの責任を分ける

### コンテナが決める

- ボタンの幅・高さ
- タップ領域
- 背景
- border radius
- focus ring
- hover / active / disabled
- 周囲との間隔

### アイコンが決める

- viewBox
- パス
- 視覚的な余白
- stroke / fill
- 光学補正

ボタンの中央からずれて見えるからといって、ボタン全体を移動させない。

---

## 5. 同じ階層で比較する

アイコン単体だけを拡大して確認しない。

下部ナビなら、リンク、検索、設定などを一列に並べて見る。

見る項目：

- 見かけの高さ
- 見かけの幅
- 黒量
- 線の密度
- ラベルとの距離
- active時の強度

「すべて20px」でも、歯車は重く、鉛筆は細く見えることがある。

必要ならパス自体を小さくする、線幅をわずかに変える、余白を変える。ただし**用途ごとに一貫した理由を持たせる**。

---

## 6. アクセシビリティ

SVG化はアクセシビリティの代わりではない。

アイコンだけのボタンでは、操作名を別に持たせる。

```html
<button aria-label="閉じる">
  <svg aria-hidden="true">...</svg>
</button>
```

確認する。

- `aria-label` または可視ラベルがある
- 装飾SVGを読み上げさせない
- 色だけで状態を示さない
- focus-visibleが見える
- 200%拡大で重ならない
- タップ領域が小さすぎない
- SVGが`currentColor`を使い、高コントラスト時にも意味を失わない

## 7. Quick Linksでの適用

2026-08-13に、Quick Linksで次を整理した。

### 起点

丸いFABの「＋」が中央からずれて見えた。

最初はCSSの二本線で修正したが、既存実装を再確認すると、後段JavaScriptですでにFABと下部ナビをSVGへ置換する仕組みがあった。

そこで、局所修正を増やさず、既存のアイコン正典へ統合した。

### 採用

- FAB：SVG
- 下部ナビ：SVG
- モーダルclose：SVG
- 検索clear：SVG
- overflow menu：SVG
- 管理画面の開閉 `＋ / −`：CSS geometry

### 学び

> 見た目のズレを見つけたとき、最初に座標を1px動かすのではなく、その記号が「文字として描かれるべきか」を問い直す。

## 8. レビュー手順

### PASS 1｜構造

- 機能アイコンと文字を分けたか
- アイコン定義が一か所にまとまっているか
- コンテナとアイコンの責任を分けたか

### PASS 2｜数値

- 共通viewBoxか
- サイズ階層が揃っているか
- stroke / cap / joinが揃っているか
- ヒット領域が十分か

### PASS 3｜光学

- 円形ボタンの中心に見えるか
- 同じ階層を並べたとき強度が揃うか
- active / inactiveで重心が動いて見えないか
- 1px補正をせずに直せる構造になっているか

### PASS 4｜環境

- iOS
- desktop browser
- 200% zoom
- キーボードfocus
- light / darkがある場合は両方

---

## 9. 失敗パターン

### フォントの＋をflex中央に置けば十分と考える

数値上の中央と字面の中心は一致しないことがある。

### ずれるたびにtranslateする

局所値が増え、別端末で再発する。

### SVGなら自動的に揃うと考える

viewBox内の余白やパスの黒量が違えば、SVG同士でも揃わない。

### タップ領域まで小さくする

見た目を洗練させても操作性を落とす。

### 全アイコンを同じパスサイズにする

同じ数値と同じ知覚強度は別物。

---

## 10. experimental運用

このルールは、Quick Linksの実装から抽象化した初期版である。

### 評価期間

2026-10-31までに、最低3つのWeb・アプリ案件へ適用し、次を確認する。

- 個別の`translate`やmargin補正が減るか
- OS差による見た目のずれが減るか
- アイコン追加時の判断が速くなるか
- アクセシビリティを落とさず統一できるか

### stableへの条件

- 3案件以上で再利用できる
- SVG／CSS geometry／文字の使い分けが破綻しない
- 例外処理が原則より増えない
- レビュー手順が実装者間で再現できる

### 撤回・修正条件

- SVG統一が実装コストだけを増やし、品質差を説明できない
- アイコンごとの個別補正が増える
- OS標準アイコンやネイティブ部品を使う方が一貫する案件が多い
- アクセシビリティ上の問題が増える

その場合、「独自アイコンを揃える原則」ではなく、「プラットフォーム標準を優先する原則」へ縮小する。
