# スマホ・インタラクション設計

> 状態：experimental  
> designmd版：2026.07.27-beta  
> 最終更新：2026-07-27

スマホ設計を、画面幅やレスポンシブレイアウトだけの問題として扱わない。

片手操作、移動、通知、強い光、騒音、通信変動、ソフトウェアキーボードなど、利用条件が絶えず変化する環境の中で、利用者が状況を理解し、判断し、操作を続けたり戻したりできる状態を設計する。

> 良いスマホ設計は、画面を小さくまとめることではない。  
> 利用者が、見える、選べる、戻れる、続けられる状態を守ることである。

この文書は、`docs/accessibility.md`を置き換えない。アクセシビリティを最低品質として通した上で、スマホ固有の注意・記憶・判断・制御・回復まで扱う。

---

## 1. 中核概念：認知主権

**認知主権（Cognitive Sovereignty）**とは、利用者が、自分の注意、記憶、判断、操作の主導権を失わない状態を指す。

これは、利用者の要求どおりに何でも即座に動かすことではない。

不可逆な削除、重大な判断、学習上必要な熟考では、あえて止めてもよい。ただし、システムによる介入には理由が必要になる。

- なぜ止められたか分かる
- 何が起きるか予測できる
- 代替手段がある
- 戻る、止める、修正することができる
- 入力や判断が黙って失われない

自動化の目的は、人の判断を消すことではなく、人が判断できる状態を支えることである。

---

## 2. 人とシステムを一つの認知・制御系として見る

画面は情報の表示場所であるだけでなく、利用者の外部記憶であり、システムを制御するための接点でもある。

したがって、次の状態を利用者の短期記憶へ任せない。

- どこまで入力したか
- 何を選択しているか
- どの位置を見ていたか
- 何のためにモーダルやメニューを開いたか
- 保存、同期、送信が完了したか
- 次にできる操作は何か

> システムが覚えられることを、利用者に覚えさせない。

スクロール位置、下書き、選択状態、処理履歴を失わせることは、単なる表示リセットではない。作業に使っていた認知資源を利用者へ再構築させることである。

## 3. 八つの原則

### 3.1 コンテキストもインターフェースの一部

端末幅だけでスマホ対応を判断しない。

姿勢、片手・両手、移動、光、騒音、通知、中断、入力方法、急ぎ、疲労、通信状態を使用条件として扱う。PCとスマホで異なる情報構造や操作方法を採用してよい。

### 3.2 注意を奪わず、必要な変化だけを前へ出す

通常状態は静かに保ち、利用者の判断や対応が必要な変化だけを強く伝える。

- 保存済み：静かに伝える
- 処理中：主作業を妨げず伝える
- 保存失敗：明確に前へ出す
- データ消失の可能性：操作を止めて確認する

モーダル、画面遷移、アニメーション、トーストを、変化が起きたという理由だけで使わない。

### 3.3 状態を見せるだけでなく、意味を理解できるようにする

スピナーや色の変化だけで意味を推測させない。

最低限、次を確認できるようにする。

- 現在のモード
- 何を処理しているか
- 進捗または待機理由
- 完了した範囲
- 失敗した範囲
- 作業への影響
- 再試行、中止、修正の可否

### 3.4 手順だけでなく、判断材料を見せる

正しい操作だけを誘導しない。

なぜ実行できないのか、何が不足しているのか、何が上書きされるのか、どの制約の中で選べるのかを示す。想定外の状況でも、利用者が目的と制約から判断できる状態をつくる。

### 3.5 操作の結果を、即座に、段階的に、取り消し可能にする

タップや入力には即座に反応を返す。大きな処理は、可能な限り小さな単位へ分ける。

- 押下状態を見せる
- 中間状態を保持する
- 途中結果を示す
- 中止、修正、Undoを用意する
- 不可逆な操作は影響範囲を明示する

### 3.6 思考の復帰までを、一つの操作として扱う

モーダルや別画面を閉じただけでは、元の作業へ戻ったことにならない。

スクロール位置、フォーカス、選択状態、入力内容、直前の目的まで復元されて、初めて操作が完了する。

画面遷移の回数ではなく、利用者が作業文脈を再構築する負担で断絶を評価する。

### 3.7 失敗を防ぐだけでなく、失敗後の回復を設計する

エラーを表示して終わらない。

- 何が失われたか
- 何が保持されているか
- 次に何をすればよいか
- 再試行、修正、退避、取り消しが可能か

を伝える。

一部の機能が使えない場合も、主要目的を継続できる代替経路を残す。

### 3.8 一つの操作方法を、唯一の正解にしない

ドラッグだけ、スワイプだけ、長押しだけ、色だけに依存させない。

同じ目的へ、タップ、ボタン、メニュー、キーボードなどの別経路でも到達できるようにする。

## 4. 摩擦には、理由を持たせる

すべてを速く、滑らかにすることを目標にしない。

不可逆な操作、重大な判断、学習上必要な思考には、意図的な停止や確認を設けてよい。一方、理由のない待機、再入力、画面移動、確認は取り除く。

摩擦は、次のいずれかへ貢献しなければならない。

1. **安全**：誤操作や損失を防ぐ
2. **理解**：影響、条件、意味を把握させる
3. **熟考**：重要な判断を急がせない

それ以外の摩擦は、原則として設計負債として扱う。

## 5. 五つの評価軸

### 5.1 Observability｜可観測性

利用者は、システムの状態と変化を理解できるか。

確認するもの：モード、進捗、保存状態、選択状態、エラー、影響範囲。

### 5.2 Controllability｜可制御性

利用者は、必要な状態へ動かせるか。

確認するもの：停止、再開、戻る、修正、上書き回避、自動処理への介入。

### 5.3 Recoverability｜回復可能性

失敗や中断の後、作業へ戻れるか。

確認するもの：未保存内容の保持、Undo、再試行、ローカル退避、元の位置への復帰、失敗理由。

### 5.4 Adaptability｜適応可能性

環境や能力が変わっても、主要目的を達成できるか。

確認するもの：低速・オフライン、片手、キーボード表示、画面回転、音声なし、ドラッグなし、長文、大量データ。

### 5.5 Cognitive Offloading｜認知の外部化

システムが、利用者の記憶や計算を適切に肩代わりできているか。

確認するもの：選択状態、下書き、次の操作、比較対象、過去結果、変更履歴。

## 6. 違和感を「失ったもの」から逆引きする

「使いにくい」で終わらせず、この違和感によって利用者が何を失ったかを確認する。

| 失ったもの | 典型的な現象 | 見直すもの |
|---|---|---|
| 状況 | 処理中か停止中か分からない | 状態表示、モード表示、進捗 |
| 位置 | 戻ったら元の箇所が分からない | スクロール、フォーカス、選択保持 |
| 操作権 | 自動処理を止められない | 中止、Undo、手動介入 |
| 入力 | エラーや画面移動で内容が消える | 下書き、退避、競合処理 |
| 判断材料 | なぜ実行できないか分からない | 制約、影響範囲、エラー文 |
| 経路 | ドラッグ以外の方法がない | 代替操作、メニュー、ボタン |
| 確信 | 押したか、保存されたか分からない | 即時フィードバック、完了表示 |

## 7. 実装仕様

### 7.1 ビューポートと安全領域

- 高さを`100vh`だけに依存させない
- `svh`、`dvh`を表示目的に応じて使い分ける
- 下部固定UIに`env(safe-area-inset-bottom)`を反映する
- ソフトウェアキーボード表示中も、入力対象と主要操作を隠さない
- 画面回転とブラウザUIの開閉で、操作不能な余白や重なりを残さない

### 7.2 タップとポインター

- WCAG 2.2の24×24 CSS pxを最低線として確認する
- 主要操作は、視認性と誤タップを考慮してより大きい領域を検討する
- 透明レイヤーや重なりがタップを奪っていないか確認する
- タップ、ドラッグ、長押しを同じ領域へ重ねすぎない
- ドラッグ操作には単一ポインターで完了する代替操作を用意する

### 7.3 入力

- 自動フォーカスは、利用者の目的が明確な場合だけ使う
- フォーカス時に画面や文脈を不必要に移動させない
- 入力対象が固定ヘッダー、フッター、キーボードに隠れない
- 未保存内容を、画面移動や一時的な閉じ操作で失わない
- 保存失敗時も入力内容を保持し、理由と回復方法を示す
- 同じ情報を再入力させる場合は理由を説明し、可能なら再利用する

### 7.4 モーダル、ドロワー、ボトムシート

- 主作業を完全に隠す必要があるか確認する
- 閉じる操作を、画面外タップだけに依存させない
- 開いた要素の内部にも、明示的な閉じる手段を置く
- 閉じた後に`overflow`、フォーカス、スクロール位置を復元する
- 不要なオーバーレイやイベント監視を残さない
- 永続する補助パネルは、フォーカス対象や主要操作を隠さない

### 7.5 状態と進捗

- 押下、待機、処理中、完了、失敗を区別する
- 進捗率が分かる場合は確定型、分からない場合は不確定型の表示を使う
- 長い処理では、現在の工程、完了件数、残件数、中止・再開方法を示す
- 部分完了を全失敗として扱わず、再開地点を残す
- 状態通知は、主作業を不必要に中断しない方法で伝える

### 7.6 自動化

- 自動保存、自動整形、自動スクロール、自動フォーカスは、制御を奪っていないか確認する
- 自動処理の対象と影響範囲を見せる
- 上書き前の状態を必要に応じて復元できるようにする
- 自動処理を停止、回避、手動修正できる経路を残す

### 7.7 低速・失敗・縮退運転

- 通信が切れても入力を保持する
- クラウド保存に失敗した場合、ローカル退避を検討する
- 音声が使えない場合、文字や視覚による代替を残す
- 一部機能が壊れても、主要タスクを継続できるようにする
- 再読み込みを唯一の復旧方法にしない

## 8. 実機確認マトリクス

最低限、次の組み合わせを確認する。

- iPhone Safari
- Android Chrome
- PCブラウザの狭幅表示
- ソフトウェアキーボード表示中
- 縦向き・横向き
- 戻るジェスチャー・ブラウザバック
- モーダルやドロワーの連続開閉
- 低速通信・オフライン
- 保存失敗・同期競合
- 長文・長いURL・大量データ
- 文字拡大・ズーム
- キーボード・スイッチ・音声入力等の代替入力

PCのデバイスエミュレーションだけで完了としない。実機で、親指の届き方、キーボード、ブラウザUI、スクロールの慣性を確認する。

## 9. レビュー項目

- [ ] 現在のモード、保存、処理状態を利用者が推測している
- [ ] タップ後に、押せたか分からない時間がある
- [ ] 入力対象やフォーカスが固定UI・キーボードに隠れる
- [ ] モーダルを閉じた後、位置、フォーカス、入力内容が復元されない
- [ ] ドラッグ、スワイプ、長押しだけでしか完了できない操作がある
- [ ] エラー後に入力内容や作業位置が失われる
- [ ] 自動処理を止める、戻す、手動修正する方法がない
- [ ] 理由のない再入力、待機、確認、画面遷移がある
- [ ] 一部機能の失敗によって、主要タスク全体が継続できなくなる
- [ ] PC版の構造を、そのまま縦積みしている
- [ ] 実機ではなく、狭幅プレビューだけで確認している

## 10. 専門的背景

このガイドは、次の考え方をスマホ・Webアプリ制作へ翻訳している。

- **Human-centred design**：利用者、目的、利用状況を開発全体で扱う
- **Distributed Cognition**：認知を頭の中だけでなく、人・道具・環境の系として見る
- **Calm Technology**：注意の中心と周辺を行き来させ、必要以上に注意を要求しない
- **Direct Manipulation**：対象を見せ、操作を段階的・可逆的にし、結果を即座に見せる
- **Ecological Interface Design**：手順だけでなく、目的・制約・関係を知覚可能にする
- **Human Factors / Use Error**：誤操作を利用者の不注意だけでなく、利用者・タスク・環境・UIの関係から分析する
- **Resilience Engineering**：失敗ゼロだけでなく、変化の中で回復・適応しながら目的を守る

## 11. 適用上の注意

- `designmd`はWCAG、JIS X 8341-3、各プラットフォームガイドラインへの適合を保証しない
- 数値を機械的に守るだけで、利用者の主導権や回復可能性が守られるとは限らない
- 重要なサービスでは、実利用者によるテスト、当事者レビュー、専門家確認を組み合わせる
- 「認知主権」を、操作を増やし続ける理由にしない。選択肢が多すぎれば、判断の主導権をかえって奪う
- 自動化を避けるのではなく、可観測・可制御・回復可能な自動化を目指す
